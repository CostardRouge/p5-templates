### Entry points, background work, integrations

- **HTTP**: pages above; API handlers under `src/app/api/` — recordings (18 handlers: enqueue, list, get/delete, start, cancel, force-cancel, retry, clone, media, thumbnail, three downloads, bulk cancel/delete/retry, control, health), progression (3, two SSE), options (download, import), `s3/[...key]` (same-origin object proxy), `assets` (temp-file reader, no caller in the repo), `sketches/form` (CORS `*`, read by steevepommier.com), `health`, and dev-only generators under `dev/` plus `thumbnails/generate`, `previews/generate` (all `notFound` in production).
- **Server actions**: `src/app/actions/notifications.ts` — `subscribeUser`, `unsubscribeUser` (imported by `MenuBar`), `sendTestNotification` (no importer).
- **Authentication**: none. No `proxy.ts`/`middleware.ts`, no session, no API key. `NEXT_PUBLIC_*` flags only hide UI.
- **Background jobs**: one BullMQ queue `recording-queue`, job `process-recording`, worker created **lazily inside the Next server process** by the first request that touches `RecordingService` (no `instrumentation.ts`, no separate process). Concurrency `WORKER_CONCURRENCY` (default 2), lock 60 s, stalled check 10 s, `maxStalledCount` 2, `attempts: 1`. No cron, no repeatable jobs, no inbound webhooks.
- **Outbound**: S3/MinIO (internal client + a public-endpoint client for presigned URLs), Redis, Postgres, Playwright Chromium against `http://localhost:3000/<sketch>`, FFmpeg child processes, web-push to stored endpoints, Umami (client-side), Watchtower HTTP API (from CI).
- **Secrets / config**: read from `process.env` at runtime — `DATABASE_URL`, `REDIS_URL`, `S3_ENDPOINT`, `S3_PUBLIC_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`, `WORKER_CONCURRENCY`, `EMBED_FRAME_ANCESTORS`; baked at build time — `BACKEND_RECORDING`, `NOTIFICATIONS`, `LIVE_THUMBNAIL`, `PREVIEW_ON_HOVER`, `INTERACTION_BINDINGS` (→ `NEXT_PUBLIC_*`), `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, `NEXT_PUBLIC_UMAMI_*`, `NEXT_PUBLIC_GITHUB_REPO_URL`. Template: `.env.example` (carried a real VAPID pair until this audit). CI secrets: `DEPLOY_WEBHOOK_URL`, `DEPLOY_WEBHOOK_TOKEN`.

### Data model (from the migrations)

| Table (model) | Columns of note | Relations | Indexes |
|---|---|---|---|
| `Template` (`Preset`) | `name` unique, `options` Json | 1-n snapshots | PK, `Template_name_key` |
| `TemplateSnapshot` (`PresetSnapshot`) | `templateId`, `options` Json | n-1 Template (cascade), 1-n Job | PK, `TemplateSnapshot_templateId_idx` |
| `Job` | `id` (client- or server-minted), `template` (`sketch`), `status` enum, `progress`, `options`/`thumbnails`/`videoUrls`/`videoSizes` Json, timing columns | n-1 snapshot (set null) | PK, `Job_snapshotId_idx` — **none on `status` or `createdAt`** |
| `PushSubscription` | `endpoint` unique, keys | — | PK, `PushSubscription_endpoint_key` |

`Preset`/`PresetSnapshot` are never queried. Every `Job` read is by id or the unbounded list (`jobStore.getAllJobs`, no `take`, no `select`). No raw SQL, no transactions. Progress lives in Redis (`recordingStatus:<id>`, no TTL). Artefacts live in S3 under `<jobId>/…`.

### Domain C — Security

ID: SEC-01 — **FIXED** `57bced2`
Severity: critical
Location: `src/app/api/assets/route.ts:21-39`
Problem: `path.join( os.tmpdir(), name )` / `folder/assets/name` from the query string; `path.join` normalises `..` away.
Impact: Unauthenticated arbitrary file read on the public host: `?name=../../../../etc/passwd` returned it with 200 (reproduced by the new test against the old route); in the container `/proc/self/environ` holds `DATABASE_URL` and the S3 keys.
Fix: Resolve with `resolveInsideDirectory` and answer 400 outside the temp dir. (Deleting the route — no caller — is DECISION-04.)
Effort: S
Risk of fixing: low
Verification: `src/app/api/assets/__tests__/route.test.ts` (4 traversal cases fail on the old handler).

ID: SEC-02 — **FIXED** `bcd1c24`
Severity: critical
Location: `package-lock.json` (next 16.3.1, sharp 0.35.3)
Problem: Next 16.0.0–16.3.5 has three RCE advisories, one in `next/og` `ImageResponse`, used by `src/app/opengraph-image.tsx`; sharp had libheif CVEs; xmldom, fast-uri, brace-expansion, js-yaml high/moderate.
Impact: Remote code execution on the public host through a published advisory.
Fix: Lockfile-only `npm update` of the named packages (next 16.3.8, sharp 0.35.5). Not `npm audit fix`, which skews the Prisma CLI ahead of the client.
Effort: S
Risk of fixing: low
Verification: `npm audit --omit=dev` 13 → 4 (the rest is Prisma CLI internals, fix = downgrade to Prisma 6); check + build green.

ID: SEC-03 — **DECISION-01**
Severity: high
Location: every handler under `src/app/api/`, `src/app/actions/notifications.ts`; no `src/proxy.ts`
Problem: No authentication or authorisation anywhere; `BACKEND_RECORDING` is not checked server-side.
Impact: Anyone can list every job and its options, delete every finished recording and its files, pause the queue for everyone, enqueue expensive Chromium + FFmpeg jobs, upload files into the bucket.
Fix: A Next 16 `src/proxy.ts` that requires a shared secret / basic auth on `/api/recordings/**`, `/api/progression/**`, `/api/options/**`, the push action, and answers 404 for the recording API when `BACKEND_RECORDING !== "true"`; keep `/api/s3/**` and sketch pages reachable from `localhost` for the capture browser.
Effort: M
Risk of fixing: medium
Verification: unauthenticated `POST /api/recordings/control` → 401; a backend recording still completes end to end.

ID: SEC-04 — **FIXED** `7aca5b6`
Severity: high
Location: `enqueue/route.ts:15,122` → `RecordingQueueService.ts:87,110-120` → `runRecording.ts:21`; `s3.ts:187` (`deleteArtifact`)
Problem: Client-supplied `jobId` was used unchecked as the S3 folder, the temp workspace path and — through the delete routes — an S3 listing prefix without a trailing slash.
Impact: `jobId=""` (accepted: `"" ?? uuid()` is `""`) then `DELETE /api/recordings/delete {ids:[""]}` deleted up to 1,000 objects of the whole bucket per call; a job named `1` deleted every recording whose id starts with 1; `..` made the temp workspace a path outside `/tmp`.
Fix: `isSafeJobId` / `isSafeObjectPath` / `isSubmittableStatus` at enqueue (400 otherwise); `deleteJobArtifacts` lists `<id>/` only, paginates, batches, refuses unsafe ids; both DELETE routes share `deleteRecordingJob`.
Effort: S
Risk of fixing: low
Verification: enqueue route test (12 of 13 fail on the old route), `deleteJobArtifacts` and `deleteRecordingJob` tests.

ID: SEC-05 — **FIXED** `c16708a` (rotation: DECISION-02)
Severity: high
Location: `.env.example:17-18`, `setup.sh:10`, `scripts/generate-vapid-keys.mjs:56-60`
Problem: A real VAPID private key was committed; setup copied it into every `.env`; the generator skipped any `.env` whose key lines existed.

ID: SEC-06 — **FIXED** `5e4ff03` (upload type allow-list: OPEN-B)
Severity: high
Location: `src/app/api/s3/[...key]/route.ts:39-48`, `RecordingQueueService.ts:109-114`
Problem: The same-origin proxy serves any bucket object with the stored type and no `nosniff`/CSP; uploads carry client file names and no explicit type.
Impact: Stored XSS on the site's origin via an uploaded `.html`/`.svg` opened at its `/api/s3` URL.

- **No per-request Prisma/Redis client changes for "scalability"** before the worker leaves the web process — they would not change the bottleneck.
