# Agent commands — the registry and the MCP server

Read when you touch `scripts/mcp/`, add a command an agent can call, or change a route or page contract those commands lean on (`/embed`, `/api/sketches/form`, `/api/recordings/*`, `window.__sketchCapture`).

## One registry, same shapes as Atelier and Winnow (2026-10-09)

**Decision.** The maintainer wants Claude (or any MCP client) to drive Sketchbook, on the conventions Atelier set the same day (`CostardRouge/atelier`, `src/shared/commands/registry.ts`, after LightCraft's `engine.execute`): every verb is a COMMAND `{ id, title, description, params, available, run }`, ids dotted and stable, run through one `execute` that checks the params first. Params are the same small subset (`number` with `min`/`max`/`integer`, `string` with `enum`, `boolean`, `strings`, `object`), turned into JSON Schema by `paramsJsonSchema`; out of range is REFUSED, never clamped; an unknown key is refused naming the known ones; `available()` answers `true` or the REASON; errors are coded `unknown | unavailable | invalid | failed`; a picture to look at is an `ImageResult` (`kind: "image"`, base64, no `data:` prefix). **Why**: an agent moving between the three projects meets one listing, one error vocabulary and one image shape. **How to apply**: keep `scripts/mcp/registry.ts` in step with Atelier's file; two deliberate differences, both because commands here reach a server over HTTP instead of a mounted screen — `available()` may be async (so `list()` is), and there is no per-screen registration stack nor `waitFor`.

## The code runs from source through Node's type stripping (2026-10-09)

`scripts/mcp/` is TypeScript run as-is by Node ≥ 22.18 (type stripping unflagged; CI and the Docker image are Node 24): a nested `package.json` makes the folder ESM, imports carry their `.ts` extension (`allowImportingTsExtensions` in the root `tsconfig.json`, legal because it is `noEmit`), type-only imports say `type`, and nothing there may use a path alias, an `enum`, a namespace or a parameter property — Node strips types, it does not compile. **Why**: one language with the app, checked by `npm run typecheck` and tested by Jest beside the logic, with no build step and no new dependency (Atelier's server is a zero-dependency `.mjs`; the same spirit). Jest compiles these files to CommonJS through ts-jest, which is fine because it only resolves the relative `.ts` imports. **How to apply**: never import from `src/` there — those files use aliases and would fail under Node; reach the app over HTTP or through the page instead.

## The command set, and which door each one uses (2026-10-09)

`app.status`, `sketches.list`, `sketches.describe`, `render.frame`, `render.video`, `jobs.get`, `jobs.wait`, `jobs.result` (`scripts/mcp/commands.ts`). **Decision: no new route, no new server code path** — each command calls what a person's gesture calls: the catalogue is the checkout's `src/sketches/metadata.json`; parameters come from `GET /api/sketches/form`; a frame is the recorder's capture protocol on the public `/embed` route (`#o=` delta, `s=WxH`) driven from headless Chromium in the MCP process (`frameRenderer.ts`, the `bench-sketch.mjs` recipe); a video is `POST /api/recordings/enqueue` exactly as the studio's Record button posts it, followed on `/api/recordings/<id>` + `/api/progression/<id>` and fetched from `/api/recordings/download/<id>`. **Why**: there is no auth (`security.md`), so a server-side "render a frame" route would be a public Chromium launcher on the NAS; this way the MCP server adds no attack surface, works against `npm run dev` or the deployment alike, and an agent's request is validated by the very routes that validate a person's. **How to apply**:
- A sketch's id is its route tail `<engine>/<category>/<name>` (also its `/embed` and `/sketches` URL); a bare name resolves when unique — two names exist in two engines.
- `options` is a nested DELTA over `formValues`, checked against the controls (`sketchForm.ts`): slider/number ranges, select values, booleans, colours as 3–4 channels 0–255, pad axes (with `field-config.ts`'s defaults: ±1, per-axis overrides), conditional groups against the branch they land on. Images, assets, item lists and device pickers are described but not checked. An unknown key is refused unless the sketch stores it without a control.
- `render.video` posts the WHOLE parameter object (`formValues` merged with the delta, arrays replaced as the option store does) over the sketch's own `options.json`, because the capture page `Object.assign`s the job's options over its defaults — a delta alone would wipe every other parameter.
- `render.frame` places the frame by `time`, `progress` or `frame`, converted with the page's own clock (`__sketchCapture.timing()`, `recording.md`); a time past the loop is refused, not wrapped.
- `render.video` and `jobs.*` are `unavailable` until `/api/recordings/health` answers (Redis + Postgres + worker; that call also boots the worker), while frames still render — a dev server without infra can do half the work.
- A failed job's REASON is not stored anywhere but the server log (the `Job` row has no error column, progression keeps only the step), so `jobs.get` names the step it died in and says so.
- Verifying a video needs the infra: `redis-server`, a Postgres with `prisma migrate deploy`, and any S3 — when the MinIO binary is unavailable, `moto_server -p 9000` plus a `PUT /recordings` bucket works, with `S3_ENDPOINT=http://localhost:9000` and any key pair. A sketch that draws at absolute pixel sizes (ping-pong's 186 px ball) does nothing at a small test size — no bounce, no sound — so test sound at the sketch's own size and a low framerate instead.
