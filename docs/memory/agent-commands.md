# Agent commands — the registry and the MCP server

Read when you touch `scripts/mcp/`, add a command an agent can call, or change a route or page contract those commands lean on (`/embed`, `/api/sketches/form`, `/api/recordings/*`, `window.__sketchCapture`).

## One registry, same shapes as Atelier and Winnow (2026-10-09)

**Decision.** The maintainer wants Claude (or any MCP client) to drive Sketchbook, on the conventions Atelier set the same day (`CostardRouge/atelier`, `src/shared/commands/registry.ts`, after LightCraft's `engine.execute`): every verb is a COMMAND `{ id, title, description, params, available, run }`, ids dotted and stable, run through one `execute` that checks the params first. Params are the same small subset (`number` with `min`/`max`/`integer`, `string` with `enum`, `boolean`, `strings`, `object`), turned into JSON Schema by `paramsJsonSchema`; out of range is REFUSED, never clamped; an unknown key is refused naming the known ones; `available()` answers `true` or the REASON; errors are coded `unknown | unavailable | invalid | failed`; a picture to look at is an `ImageResult` (`kind: "image"`, base64, no `data:` prefix). **Why**: an agent moving between the three projects meets one listing, one error vocabulary and one image shape. **How to apply**: keep `scripts/mcp/registry.ts` in step with Atelier's file; two deliberate differences, both because commands here reach a server over HTTP instead of a mounted screen — `available()` may be async (so `list()` is), and there is no per-screen registration stack nor `waitFor`.

## The code runs from source through Node's type stripping (2026-10-09)

`scripts/mcp/` is TypeScript run as-is by Node ≥ 22.18 (type stripping unflagged; CI and the Docker image are Node 24): a nested `package.json` makes the folder ESM, imports carry their `.ts` extension (`allowImportingTsExtensions` in the root `tsconfig.json`, legal because it is `noEmit`), type-only imports say `type`, and nothing there may use a path alias, an `enum`, a namespace or a parameter property — Node strips types, it does not compile. **Why**: one language with the app, checked by `npm run typecheck` and tested by Jest beside the logic, with no build step and no new dependency (Atelier's server is a zero-dependency `.mjs`; the same spirit). Jest compiles these files to CommonJS through ts-jest, which is fine because it only resolves the relative `.ts` imports. **How to apply**: never import from `src/` there — those files use aliases and would fail under Node; reach the app over HTTP or through the page instead.

## The command set, and which door each one uses (2026-10-09)

Sixteen commands in four files (`scripts/mcp/commands.ts` assembles them; `context.ts` holds the shared HTTP helpers and probes): `app.status`, `sketches.list`, `sketches.describe`, `options.schema`; `render.frame`, `render.stills`, `render.video`; `jobs.get`, `jobs.wait`, `jobs.result`, `jobs.list`, `jobs.cancel`; `drafts.create`, `drafts.update`, `drafts.get`, `drafts.copy`. **Decision: no new server code path for an action** — each command calls what a person's gesture calls: the catalogue is the checkout's `src/sketches/metadata.json`; parameters come from `GET /api/sketches/form`; a document is checked by `POST /api/options/validate` (the only routes added, both pure — `security.md`); a draft is the studio's Save draft (`POST /api/recordings/enqueue`, `status=draft`, files as `file[global][<kind>]`); a frame is the recorder's capture protocol driven from headless Chromium in the MCP process (`frameRenderer.ts`, the `bench-sketch.mjs` recipe); a video is the recording pipeline, followed and fetched through the dashboard's routes. **Why**: there is no auth (`security.md`), so a server-side "render" route would be a public Chromium launcher on the NAS; this way the MCP server adds no attack surface, works against `npm run dev` or the deployment alike, and an agent's request is validated by the very code that validates a person's. **How to apply**:
- A sketch's id is its route tail `<engine>/<category>/<name>` (also its `/embed` and `/sketches` URL); a bare name resolves when unique — two names exist in two engines.
- `options` is a nested DELTA over `formValues`, checked against the controls (`sketchForm.ts`): slider/number ranges, select values, booleans, colours as 3–4 channels 0–255, pad axes (with `field-config.ts`'s defaults: ±1, per-axis overrides), conditional groups against the branch they land on. Images, assets, item lists and device pickers are described but not checked. An unknown key is refused unless the sketch stores it without a control.
- Two ways to make a piece. Quick: `render.frame` / `render.stills` / `render.video` on a `sketch` with a delta, size and clock — rendered on `/embed` (frames) or posted as a queued job (video). Whole: a DRAFT (`drafts.ts`) holds the full document — content items (text, title, image, QR code, HUD, sketch layers), slides, size, clock, the sketch's parameters — and uploaded media; frames render on the draft's own studio page (`/sketches/…?id=<draft>&capturing`, the page the recorder loads), so a still and the video come from the same document.
- Any document a command stores carries the sketch's parameters WHOLE (`formValues` merged with the delta, arrays replaced as the option store does), because the capture page `Object.assign`s the job's options over its defaults; and its other keys as `/api/options/validate` normalises them (below).
- `render.video { draft }` clones the draft (`/api/recordings/<id>/clone`) and starts the copy: a job records once, and the safest default is that the draft stays editable. `drafts.update` refuses anything not in status `draft`; `drafts.copy` makes an editable draft from any job.
- `drafts.update` re-sends every file the draft keeps (fetched back from `/api/s3/<id>/assets/…`): the enqueue route rebuilds `assets` from the files in the request, as the studio's own re-save does. A slide asset whose slide a new `slides` list removed is dropped and reported.
- Uploaded media are referenced as `global/<images|videos|audios>/<name>` (`getScopeAssetPath`); the name is reduced to `[A-Za-z0-9._-]`. `readMedia` reads only media extensions, ≤ 500 MB: an agent could otherwise be talked into uploading any file the user can read to a public server.
- `render.frame` places the frame by `time`, `progress` or `frame`, converted with the page's own clock (`__sketchCapture.timing()`, `recording.md`); a time past the loop is refused, not wrapped. `render.stills` takes `count` positions `from + (to − from)·i/count` (end excluded so a closed loop does not repeat), renders them in ONE page load, saves each PNG and answers a contact sheet.
- An odd width or height is recorded padded to even by the recorder (`recording.md`), so `render.video` no longer refuses it: its answer carries `padded`, one line per size that will change (540 × 675 → 540 × 676), so the agent is not surprised by the file.
- `render.video`, `drafts.*` and `jobs.*` are `unavailable` until `/api/recordings/health` answers (Redis + Postgres + worker; that call also boots the worker), while frames of a sketch still render — a dev server without infra can do half the work.
- A failed job's reason comes from `Job.error` (`recording.md`); against a server older than that column `jobs.get` falls back to the step it died in and says the reason is in the log.
- A page that throws while it loads never becomes ready; the renderer then reports the page's errors instead of a bare timeout.
- Verifying a video needs the infra: `redis-server`, a Postgres with `prisma migrate deploy`, and any S3 — when the MinIO binary is unavailable, `moto_server -p 9000` plus a `PUT /recordings` bucket works, with `S3_ENDPOINT=http://localhost:9000` and any key pair. A sketch that draws at absolute pixel sizes (ping-pong's 186 px ball) does nothing at a small test size — no bounce, no sound — so test sound at the sketch's own size and a low framerate instead.

## The MCP server is a local stdio process with Atelier's three tools (2026-10-09)

`scripts/mcp/sketchbook-mcp.ts` speaks MCP (JSON-RPC 2.0, one message per line) over stdio; `protocol.ts` is the pure handler. Three generic tools, named like Atelier's: `sketchbook_status` (= `app.status`), `sketchbook_commands` (every command, `paramsJsonSchema`, availability and reason), `sketchbook_run` (`{ command, params }` → `execute`). An `ImageResult` becomes an MCP image block followed by its note; a `CommandError` becomes `isError: true` with `"<code>: <message>"`. **Why generic tools rather than one per command**: the registry is the list, so a new command is callable at once, and availability is read when asked rather than frozen at `tools/list`. **Why stdio in the checkout rather than an MCP endpoint inside the app**: no auth (`security.md`) — an HTTP MCP route on the NAS would hand every caller a render queue; the local process reaches the deployment only through routes that are already public. A remote endpoint is the maintainer's call and would need a token first. **How to apply**: stdout is JSON-RPC only — log to stderr; calls run concurrently (a `jobs.wait` must not block a `ping`); one Chromium is kept for the server's life, one context per frame. Configuration is environment only: `SKETCHBOOK_URL`, `SKETCHBOOK_OUTPUT_DIR`, `PW_CHROMIUM`. `claude mcp get sketchbook` reports `√ Connected` on a working install.

## Not done yet (2026-10-09)

- No command writes a preset (the `Preset` model), only drafts and jobs. The studio MCP saves and reopens a piece through the browser gallery instead (`gallery.*`, 2026-10-11 — `gallery.md`).
- A front-end export (several variants — Reel, square — from one run, GIF, image sequence) has no server equivalent; an agent gets MP4 per slide, and stills through `render.stills`.

## A stored job's options reach the page UNPARSED — store the normalised document (2026-10-09)

The sketch page `Object.assign`s a job's `options.json` over `OptionsSchema.parse( {} )`; the job's own content items, slides and sizes are never run through the schema, so their zod defaults are never filled. The studio never notices because its form writes complete items. A hand-built `{ type: "text", content: "hi" }` therefore reaches the text renderer without `alignment` and throws on every frame (`Cannot read properties of undefined (reading 'horizontal')`) — the page never becomes ready, so a frame render times out and a recording fails at `waitForSelector`. **How to apply**: anything that writes a job's options by hand takes `normalized` from `POST /api/options/validate` (the parsed document, defaults filled) for the keys it supplies, never the raw input. Restrict to the supplied keys: the parse also fills root defaults (1080 × 1350, 60 fps / 12 s) that would override the sketch's own `options.json`.

## Level 1: a studio TAB driven through a relay the person runs (2026-10-10)

**Decision.** The maintainer wants two levels: level 1 drives an open studio tab (his front-end export, his GPU, his encoders — and it works on any deployment, static included), level 2 is the headless server path above. Level 1 copies Atelier's bridge: `scripts/mcp/studioRelay.ts` is an MCP server on stdio that relays to ONE tab over `127.0.0.1:7982` (SSE down, POST `/message` back, POST `/file` for exported files written under `--out`, default `~/Movies/Sketchbook`, never outside it, never over a file). **A server-side relay was considered and rejected**: Claude Code can reach an MCP server over HTTP, so the Next server could relay to a tab, but it would not exist on a static deployment and would be a public, unauthenticated route that steers tabs (it would need a pairing token). **The relay is served by every deployment** as `/mcp/sketchbook-studio-mcp.mjs` so nobody needs the repository: `studioRelay.ts` imports Node modules only, `npm run mcp:relay:write` compiles it with the locked `typescript` (`relayBuild.ts`; Node's own `stripTypeScriptTypes` is experimental and could drift), and `studioRelay.test.ts` fails when the committed file is stale or imports anything but `node:*`. **How to apply**:
- Security is the Origin check (`originAllowed`: loopback on any port, `https://p5.steeve.website`, `SKETCHBOOK_ORIGINS`), a browser cannot forge it; no Origin (curl) is refused. Chrome's Local Network Access asks a public page's preflight for `Access-Control-Allow-Private-Network: true`, which the relay answers.
- A newer tab replaces the older (`event: replaced`); pending calls fail with a sentence when the tab goes; a run may last 30 min (an export), a listing 15 s.
- Tools: `sketchbook_studio_status` / `_commands` / `_run` — the level-2 server keeps `sketchbook_*`, so both can be registered side by side.

## The tab's commands go through the FORM, registered beside the selection listener (2026-10-10)

**Decision.** `StudioCommands` (`SketchOptions/components/StudioCommands.tsx`) is mounted inside `FormProvider` → `FormUndoRedo` → `ContentSelectionProvider`, beside `ContentSelectionListener`, and registers the commands of `src/lib/agent/commands/` into `studioCommands` (`src/lib/agent/studioBridge.ts`, the same `scripts/mcp/registry.ts`, imported across — Next compiles the `.ts`-suffixed import) while the form is mounted. Every write is `form.setValue( path, value, { shouldDirty, shouldValidate } )` leaf by leaf (`leafWrites`, arrays whole). **Why the form and not the option store**: the form is the source of truth — it reaches the engine through `SketchPage`'s flush, the undo history (`FormUndoRedo` auto-captures it), autosave and the next save; `setSketchOptions( x, "react" )` from outside reaches the engine only (both subscribers skip `"react"`) and a later full flush overwrites it, and `"p5"` reaches the form but p5 skips its own origin, so a size change never re-lays the canvas out. Slides go through `useSlideManagement`'s handlers (never `window.setSlide` alone: the active index lives in that hook and the context), play/pause through the transport's pair (engine + `SET_LOOPING`), seek through `getAnimationBridge()`, the snapshot through `captureFreshPngBlob`. **How to apply**: a new command takes a `StudioHandles` member (`src/lib/agent/handles.ts`) wired to the control's own call, never a store write; commands are pure over the handles and tested with `__tests__/fakeHandles.ts`. `window.sketchbook.commands()` / `.run( id, params )` is the console's (and Playwright's) door to the same registry. The menu's "Connect an agent" opens the stream (`connectBridge`), and a green dot on the menu button says a tab is driveable. The commands are absent until the sketch has loaded and while `?capturing`, because the form is.

**Verified headless** (2026-10-10): the served relay on stdio, a studio tab connected by clicking the menu, then over MCP — a refused `hueSpeed: 9`, `sketch.set` palette + sites, `playback.seek` 0.5, a snapshot showing both, `canvas.set` 1080×1080 re-laying the canvas out square, `history.undo` restoring 1080×1350.

## Content commands: check the merged item first, place by the DRAWN centre (2026-10-10)

`content.add` / `content.update` build `{ type, ...fields }` (or the merged item) and run it through `validateOptionsDocument` before any write, so an unknown key (`fontSize` on text, `content` on a HUD widget) is refused naming the known ones instead of being silently dropped by zod; only then does `makeDefaultItem` fill the defaults. `content.place` takes x,y as where the item's VISIBLE centre goes, not the stored field: a text/title `position` is the corner of a layout box as wide as the canvas (`drawSlideText`: `(margin + position) * size`), so writing 0.5 put a centred text's middle at the right edge. It reads the rectangle the renderer reported to `itemBoundsRegistry` (p5 only; a slide's items only while that slide is on screen) and moves the field by the gap — the field translates the drawing for every placed type. Stored coordinates are 0–1 (`Vec2` snaps anything else to 0.5 on load), so a centre the field cannot reach is refused, and for text the message points at `alignment` — a centred text's centre only spans 0.5–1.5 of the field. `by: "field"` writes the raw value. `content.duplicate` inserts right after its source, shifting every later index.

## Slide commands answer only once the filmstrip has landed (2026-10-10)

`slides.*` call `useSlideManagement`'s handlers, which land their effects a render or more later: add/duplicate select through `pendingSelectIndexRef`, and every switch is deferred behind the OUTGOING slide's thumbnail capture (bounded, but well over 150 ms under SwiftShader). Each command therefore polls (`until`) for the exact state the handler will reach — the new count AND the index it selects — rather than a quiet window, which answered `slides.remove` with a stale index. `activeAfterRemoval` mirrors `handleDeleteSlide`'s re-selection; change both together.

## Export commands share the dialog's variant list and runner; files go to the relay (2026-10-10)

`export.*` edit the SAME per-sketch list as the Export dialog (`variantStore`, keyed `<engineId>/<name>`), so what an agent adds is there when the person opens Export, and run it through `runExportBatch` with `form.getValues()` as options — exactly the panel's call. Delivery is the relay only: each artifact is POSTed to `/file` as its variant lands (a cancel keeps what was written), so `export.run` is unavailable without a connected relay; nothing downloads in the tab. Refused rather than bent: a framerate above the sketch's own (the runner would `Math.min` it), width without height, frameCount with allFrames, variant fields on a list run (they shape a one-off `preset` run, which joins no list). One run at a time (module-level), with `export.status` / `export.cancel` answering while `export.run` is still awaiting — the bridge answers each relay message independently. The agent's run does not show in the dialog's table (its progress is panel state). Headless Chromium has no H.264 encoder: verify with `format: "webm"`.

## Media commands register a blob in the tab, like the picker (2026-10-10)

`assets.add` takes base64 `data` or a `url` the TAB fetches (`credentials: "omit"`; a server without CORS refuses, and the error says to send data instead), builds a `File`, and goes through `useAssetDrop().addAssets` via a `DataTransfer` FileList — the picker's own path (HEIC normalisation, unique scoped path) — then writes the path into the form's `assets.<kind>` as `useAssetsBridge` does, because `addAssets` alone writes the option store, not the form. The asset lives in the tab like a picked file. Image items read `source` (an images-stack `sources`), not `src`: `assets.remove` refuses while an item shows the file. 50 MB cap, a name with an extension, no folders. The relay could read a local path for the agent, but that was left out: it would be a file-read primitive behind a browser origin check.

## Opening a sketch is a client navigation the command waits out; "has changes" = the undo stack, flushed (2026-10-10)

`studio.open` does `router.push('/sketches/<path>')`: the bridge's EventSource is module-level and survives it, the old form's commands unregister on unmount and the new sketch's register on mount (`setBridgeSketch`), and the command — still running in the old closure — polls `getBridgeSketch()` until it names the target (60 s). The app has no dirty-state guard, so the command keeps one: refused while there is anything to undo, unless `discard: true`. Trap: `FormUndoRedo` captures 400 ms after the last change, so `canUndo` right after an agent's write was still false (the guard let a fresh edit go, `history.undo` was "unavailable"). The handles call `capture()` (a no-op when nothing changed) and read `getHistory()`'s stacks instead of the React flags; `undo()` already flushes on its own.

## `studio.contactSheet`: the loop in one picture, the tab put back (2026-10-11)

`studio.contactSheet` answers N frames (default 6, max 12 — a 12-frame sheet of a 1080 × 1350 canvas is already 4 × 3 cells at ~250 px on a 1024 px edge) spread `from`..`to` (end excluded, as `render.stills`) as ONE `ImageResult`, drawn in the tab by `framesToContactSheet` (`imageResult.ts`: the server's `sheetGrid` layout, grey gaps, a `0 %`…`83 %` caption per cell drawn AFTER scaling so it stays legible). It is `playback.seek` + `studio.snapshot` in a loop — pause, `setProgression` + `redraw`, one macrotask, `captureFreshPngBlob` — so every engine's seek works unchanged (verified p5, GSAP and Three.js: 1.8 / 3.4 / 5.9 s for six frames under SwiftShader). The restore is in a `finally`: back to the position read first, and `play()` only if it was playing — a frame that cannot be read leaves the tab where the person had it. **Trap it exposed**: `isPlaying()` read `state.looping`, a context flag that lands a render after `dispatch`, so a sheet asked right after `playback.seek` saw "playing", and resumed the sketch it had just paused (seen on GSAP, where the render came later). `StudioCommands` now keeps the commands' own play/pause INTENT until the flag moves; any command that must restore the transport reads that, never the flag alone. **Pick a count that does not divide the sketch's beat count**: a 4-frame sheet of `flip-v1-letter-cycle` (four half-turns per loop) showed four identical edge-on hairlines, since every sample fell on the one frame where the plane is flat; 5 frames showed the four glyphs. The same holds for any sketch with N identical beats per loop.

## One agent request = one undo step: a transaction around every `run`, and `studio.batch` (2026-10-11)

**Measured first** (headless, counting `history.undo` until "nothing to undo"): `FormUndoRedo`'s 400 ms debounced capture groups by TIME, not by request — a `sketch.set` of three leaves was one step, but two `sketch.set` requests back to back (an agent's pace) folded into ONE step, `content.add` + `content.place` were two, and a request writing across more than 400 ms would split. `startBatch` / `endBatch` only tag entries with a `batchId`: `mergeBatchEntries` is never called on the undo path (`compressHistory` just slices), so they group nothing. **Decision**: `StudioCommands` wraps every command's `run` (`withTransactions`, `src/lib/agent/transaction.ts`) in `handles.transaction`: `capture()` first (the person's pending edit becomes its own step), `pause()`, run, `resume()`, `capture( "agent: <id>" )` in a `finally` — one entry per request, none when nothing was written (capture diffs against the last committed state), and a refused call never opens one (params are checked before `run`). Nesting is a depth counter, so `studio.batch` — a list of `{ command, params }` run in order through the same registry — is one step for all of them; it stops at the first failure, keeps the steps before it (one undo step, said in the error) and refuses `studio.open`, `export.run`, `history.*` and itself as steps. Those four are also left out of transactions (`UNGROUPED_COMMANDS`): `studio.open` unmounts the form and its history, `export.run` may run 30 min (pausing capture that long would fold the person's edits into the agent's step), undo/redo are the history's own moves. **Verified**: two back-to-back `sketch.set` = 2 steps, a batch of `sketch.set` + `canvas.set` + `content.add` = 1, `slides.add` = 1, `studio.snapshot` = 0, a batch failing at step 1 = 1 (step 0 kept), and one keyboard Ctrl+Z after a batch restored size, hue and palette together. Not measured in the tab: a person's slider edit made < 400 ms before an agent write (the voronoi form exposes no `input[type=range]` to Playwright at that viewport); the flush at the start of the transaction is what keeps it separate. The registry gained a `objects` param type (a list of objects) for the batch's `steps` — **a divergence from Atelier's subset to port there** (`registry.ts`, `paramsJsonSchema` → `array` of `object`).

## Binding commands go through the affordance's write path, extracted (2026-10-11)

`bindings.targets` / `bindings.list` / `bindings.add` / `bindings.update` / `bindings.remove` (`bindingCommands.ts`) edit the `interactive.bindings` list beside a slide's (or the root's) `sketch` scope. **Decision**: the affordance's three inline writes — store the list, flip a live source's `interaction.*` enable flags (seeding the inert block, lazily importing `defaults.js`), prune the block once nothing needs it — were extracted to `BindingAffordance/bindingWrites.ts` and the component now calls them, so the agent and a click share ONE write path rather than a copy. A new binding is `makeDefaultBinding` (the editor's own defaults: oscillator over the control's whole range, a colour ramp from the current colour, the enum's values copied), then the named `source` / `project` with `switchCategory`'s generator seed (`generatorSeed` in `StudioCommands`), then the agent's `fields` over it — unknown keys refused naming the editable ones, a source checked against `channelSourceOptions( kind )` plus the five generators (a pad takes vector channels only), `target` and `kind` never given (they come from the control, walked out of `formConfiguration` by `bindableTargets`). The commands are `unavailable` when `interactionBindingsEnabled()` is false, as the affordance is absent then: the flag is baked at build time (`INTERACTION_BINDINGS=true`), so a dev server started without it answers "off in this build" for all five. MIDI learn and sketch-declared `binding: { control }` are not reachable from the commands. Note that the picker offers the input channels to EVERY scalar kind (an enum walked by `mouse` · x is legal, the signal is quantized), and only a pad is restricted to vector channels — a source check must mirror `channelSourceOptions`, not assume generators-only for enum/boolean/colour. **Verified** on voronoi-v1 under `INTERACTION_BINDINGS=true npx next dev`: 111 bindable targets; a ramp on `render.hueSpeed` (mapping 0.2–3), a sequence on `sites.count` (seeded with stops [2, 120] from the mapping), the enum default on `render.palette` (sawtooth over its six values), mouse · x at weight 0.5 / blend add; the engine then published `--binding-value-render-hueSpeed` moving (1.87 → 2.46 across 2.5 s), `-sites-count` at 120 and `-render-palette` stepping 3 → 4 while `sketch.render.hueSpeed` stayed at its base 0; update to oscillator kept the ramp block (as the popover's category switch does); remove shifted the indices; each request was one undo step (five undos took back five of the seven writes).

## Two MCP apps share one relay: the second FOLLOWS the first (2026-10-11)

Claude Desktop and Claude Code each start their own `sketchbook-studio-mcp.mjs`, and only one can hold 127.0.0.1:7982; the second used to answer "port taken" to every tool. Ported from Atelier's bridge fix (its #297, `scripts/atelier-mcp.mjs`) so the two relays stay one idiom: the relay that binds is the HUB; one that hits `EADDRINUSE` asks `GET /peer/status` and, if a Sketchbook relay answers, FOLLOWS it — tool calls go through `POST /peer/relay`, the tab and the output folder are the hub's. `/peer/*` refuse any request with an `Origin` (every browser sends one) and need a 32-byte bearer token the hub writes to `~/.sketchbook/relay-<port>.token` (dir 0700, file 0600, removed on exit), compared in constant time (`peerAuthorized`, `parsePeerRequest`, tested). Beyond Atelier: the follower polls its hub every 5 s and takes the port as soon as it quits rather than at its next tool call, because the tab is retrying meanwhile. **Tab side trap**: `connectBridge`'s `onerror` gave up on any error before a `welcome`, and the browser's first retry after the hub dies fails before the follower holds the port — so a once-welcomed connection now keeps retrying (`everWelcomed`); only a relay that NEVER answered is given up on. **How to apply**: a change to the relay's handshake belongs in both repos; verify with two relays from the served file, one tab, then quit the first (the follower answers from the same tab within ~10 s).

## The relay also ships as a Claude Desktop extension, committed and drift-tested (2026-10-11)

`public/mcp/sketchbook-studio.mcpb` is a stored ZIP (`scripts/mcp/zipStore.ts`, ported from Atelier: fixed DOS timestamps, no compression, so the same input is the same bytes) of `manifest.json` (`bundleManifest()` in `relayBuild.ts`, MCPB `manifest_version` 0.3, `${__dirname}` in the args) and the built relay under `server/`. Opened, Claude Desktop installs it from a dialog and runs it with its own Node — no terminal. Atelier GENERATES its copy at build (Vite plugin); here it is COMMITTED beside the `.mjs`, written by the same `npm run mcp:relay:write`, and `studioRelay.test.ts` fails when either drifts — Next has no build hook as cheap as a Vite plugin, and a committed file is served even by a static export. Verified: Python's `zipfile` reads it, and its extracted server answers `initialize`. Not yet installed in a real Claude Desktop. **How to apply**: bump `RELAY_VERSION` when the relay's behaviour changes — it is the extension's version, and Claude Desktop compares it on reinstall.

## The setup guide is a dialog from the menu, not a page (2026-10-11)

"Agent setup guide" in the menu opens `AgentGuideDialog` (lazy, headlessui `Dialog`): three steps over the live bridge state — add the relay to your AI app (Claude Desktop → the `.mcpb`; Claude Code → one curl + `claude mcp add` line built from `window.location.origin`; Other → an `mcpServers` block with a typed path), connect, ask (copyable prompts) — then a folded "Good to know". Same shape as Atelier's `#/agents` page. A dialog rather than a route because the menu is on every page while the commands exist only on a sketch page: the guide says so when connected elsewhere.
