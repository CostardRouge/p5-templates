# Recording

Read before touching capture, the job queue, the Playwright/FFmpeg path or how artefacts are stored.

## One capture contract, two runners

2026-08-20 — In-browser recording and headless backend recording are not two implementations: both drive the engine's deterministic capture methods (`beginDeterministicCapture`, `seekAndDraw`, `captureFrame`) through `src/engines/recording/`. What differs is the recorder strategy (`RealtimeRecorder` vs `AsyncLoopRecorder`) and the encoder (`MediabunnyEncoder`, `GifEncoder` in-browser; FFmpeg on the server). **How to apply**: a capture bug is usually in the engine's capture implementation, not in the recorder — fix it there and both paths benefit. Adding an output format means an encoder, not a second pipeline.

## The backend path, end to end

2026-08-20 — `POST /api/recordings/enqueue` validates options, persists a `Job` through `src/lib/jobStore.ts` and enqueues on BullMQ (Redis). `RecordingWorkerService` — a singleton with configurable concurrency — picks it up and calls `src/lib/runRecording.ts`, which allocates a temp workspace under `os.tmpdir()/<jobId>`, then `src/lib/recordSketch.ts` drives headless Chromium over the sketch route, captures frames deterministically, and FFmpeg encodes them. Outputs upload to S3/MinIO. Progress is reported through `src/lib/progression/` as named steps, which is what the dashboard streams. **How to apply**: when a recording fails, the job row and its progression steps say which stage died — read them before instrumenting anything. The whole path is gated by the `BACKEND_RECORDING` flag (`docs/memory/architecture.md`), so with the flag off it is simply absent, not broken.

## Multi-slide recordings produce arrays

2026-08-20 — A sketch with `options.slides` records one video per slide, so a job's `videoUrls` and `thumbnails` are arrays even for the single-slide case (`recordSketch.ts` writes a one-element array). Between slides the recorder re-navigates and waits on a `[data-slide="<n>"]` selector — deliberately engine-agnostic: p5 sets that attribute on its canvas, DOM engines on their root element. Per-slide settings are the slide's override merged over the sketch's animation config. **How to apply**: never assume a single video URL when consuming a job. If a new engine is added, it must set `data-slide` or multi-slide capture will hang waiting for a selector that never appears.

## FFmpeg is a runtime system dependency

2026-08-20 — FFmpeg is not an npm package here: the Docker runtime stage `apt-get install`s it, and both Docker stages start from `mcr.microsoft.com/playwright:v1.59.1-jammy` so headless Chromium and its system libraries come pre-installed rather than being downloaded at build time. **How to apply**: backend recording on a bare machine needs FFmpeg on `PATH` and Playwright's browsers installed — it will fail at encode time otherwise, not at startup. When bumping `playwright` in `package.json`, bump the Dockerfile base image tag to match; a mismatch between the npm client and the image's bundled browser is the failure mode to expect.

## Front-end export is a list of variants, not one recording

2026-08-29 — The export modal drives `src/lib/export/runExportBatch.ts` over a list of `ExportVariant`s (`src/lib/export/variants.ts`), each with its own resolution, framerate, format and slide scope, so one sketch yields a Reel and a square post in a single run. Each variant is a *genuine re-layout*: the runner pushes `size` + `animation.framerate` into the option store, captures, and rolls back — it does not capture once and rescale. **How to apply**: a new output shape is a new variant field plus a branch in `runVariant`, never a second pipeline; `src/engines/recording/` stays untouched and is consumed as-is.

## The export override protocol, and the three traps it exists for

2026-08-29 — `src/lib/export/overrideScope.ts` is the only sanctioned way to change canvas size or framerate for a capture. Always as a scope: `applyExportOverrides()` then `restore()` in a `finally` — a run that throws or is cancelled must never leave the studio at 1080×1920. Three traps it closes, each of which produced a silently wrong file rather than an error:

- **A global `size` push is masked by per-slide overrides.** p5's `getEffective()` (and the GSAP runtime) merge the active slide's `size` *over* the global value, so `setSketchOptions({ size })` on a deck whose slide carries its own size resizes nothing. The override therefore replaces the whole `slides` array with one stripped of every per-slide `size`/`animation` — arrays are leaf values to the store's merge, so this swaps them wholesale. A variant's explicit resolution consequently wins over per-slide sizes, which is also why mixed slide sizes can only arise when a variant is set to "sketch's own size".
- **`window.setSlide()` re-applies the slide's own size and framerate** (`slides.applyEffectiveSettings`), so every slide switch inside a run must be followed by `handle.reapply()`. Switch the slide *first*, re-apply *second*; the reverse silently reverts.
- **The settle is budgeted in FRAMES, not milliseconds.** It waits on the engine's own render loop, and a heavy sketch on a software renderer can take *seconds* per frame — measured at ~7s for two frames on a raymarcher under SwiftShader. A wall-clock budget aborts those exports for being slow rather than for being wrong. It also returns immediately when the surface already matches on the first look: no resize was needed, so there is nothing to settle, and waiting the stability window would cost two frames on the commonest case there is. Only frames the engine actually *drew* are counted — see the `requestAnimationFrame` entry below.
- **The resize is not synchronous on every engine**, and `AsyncLoopRecorder` snapshots the encoder's dimensions once at `start()` — so reading early bakes the wrong size into the whole clip, not one frame. `applyExportOverrides` polls the capture source until it holds the target for two frames, then fails loudly rather than encoding at the wrong size. p5 calls `pixelDensity( 1 )` (`src/sketches/p5/utils/sketch.js`), so the backing store matches the declared size 1:1 and a direct comparison is meaningful — there is no DPR fudge to apply.

## `requestAnimationFrame` is not a promise the browser keeps

2026-08-31 — Every wait in the export path goes through `src/lib/export/nextFrame.ts`, which races rAF against a 250 ms timer and reports which won. A raw `await new Promise( requestAnimationFrame )` is a **hang**, not a delay: a hidden tab, a minimised window or a software renderer with nothing left to composite stops delivering frames outright, and the loops around these waits only check their deadline *between* frames — so the export sits on "Preparing…" forever instead of finishing or failing. Reproduced in the container (headless Chromium/SwiftShader idles at ~0.5 fps and drops to zero once the sketch stops drawing); a user backgrounding the tab mid-export hits the same thing. **How to apply**: never `await` a bare rAF inside an export loop, and when a budget is counted in frames, count only waits where `framed` is true — spending it on timer ticks the renderer had no part in reintroduces the wall clock the frame budget exists to avoid. `overrideScope.test.ts` pins both halves with a rAF that is never called back.

## The export runner owns the option store while it runs

2026-08-29 — `SketchContextProvider` re-pushes the form's options on *every* form tick, which mid-capture would resize the canvas under a running encoder. `src/lib/syncSketchOptions.ts` therefore has a suspend gate: `suspendReactSketchOptionsSync()` buffers `origin === "react"` updates and `resume…()` replays the last one, so a slider dragged mid-export lands after the run instead of corrupting it. **The runner's own writes use `origin: "export"`** — without a distinct origin they are swallowed by the gate the runner just raised and nothing ever resizes. That bug is invisible by inspection (every call succeeds, the canvas simply never changes); `src/lib/export/__tests__/overrideScope.test.ts` is what caught it and what will catch it again.

## Combined multi-slide video: one encoder, no concat, no audio

2026-08-29 — `src/engines/recording/createSlidePlaylistHost.ts` presents several slides as one continuous frame range, so `AsyncLoopRecorder` writes a single file directly. There is no ffmpeg in the browser, so capturing into one encoder is the only route to a joined clip — a concat step was never available. Two constraints: **frame indices are global to the recorder but local to the engine** (the deterministic clock renders frame `n` at `t = n / frameRate` and does not wrap, so a global index would draw the second slide past the end of its own loop), and **every slide must be forced to one resolution first** because the encoder cannot change dimensions mid-stream. Audio is deliberately off for this path (`createRecorder({ audio: false })`): the audio engine timestamps events against the deterministic clock, which restarts per slide, so one offline render would stack every slide's sound onto the first slide's span. Slides join as hard cuts — `slides[i].transition` is not applied.

## The front-end export preview, and why sharing is not downloading

2026-08-31 — A finished variant's blobs reach the panel through a second callback, `onArtifacts( variantId, artifacts )`, called after `deliver()` so a preview never delays the download the user is already waiting on. It is deliberately *not* a field on `ExportItemState`: that type is the progress feed, copied for every listener on every frame, and is no place for blobs. `ExportPanel` holds them only while the dialog is mounted, and `ExportPreview` renders straight from `URL.createObjectURL( blob )` — which is also why it needs none of the `/api/s3/[...key]` proxy the backend preview does (WebKit refuses a `<video>` whose source cannot serve range requests; a `blob:` URL can).

The preview exists for a need a download cannot meet: **on iOS a `<a download>` only ever reaches the Files app, and no web API writes to Photos.** The native share sheet's "Save Image" / "Save Video" does, so `navigator.share({ files })` (`src/lib/export/share.ts`) is the only route from a browser export to the camera roll. Capability is decided by `navigator.canShare({ files })` and never by sniffing the user agent — file sharing is gated on platform, secure context and file type at once. A dismissed sheet (`AbortError`) is a normal outcome and must not fall through to a download: re-downloading behind the user's back is the exact behaviour this feature exists to avoid. A `.gif` previews as an `<img>`, not a `<video>` — it is not a video container and a `<video>` renders nothing for it, silently.
