# Studio UI — the sketch preview page layout

Read before touching the sketch page's panels, the docked/floating layouts, the mobile drawer, the filmstrip or the export surface.

## The layout model (2026-08-28)

One inspector, a content rail, a filmstrip, export in the top bar. Decided with the maintainer over an interactive mockup (conversation "sketch-preview-interface"); the data model was explicitly out of scope — only placement changed.

- **Inspector (left)** — `SketchSettings`: a "canvas & animation" section (`RootSettings`, editing `format`/`animation`) above the sketch's own form, one action bar pinned at the bottom (reset / randomize / apply-to-all-slides · ui-sound far right, plus save-defaults / thumbnail / preview only while the dev actions are switched on). The panel exists even when the sketch has no `formConfiguration` — canvas settings must never disappear — so `SketchPage.reserveLeft` is simply `dockedDesktop`.
- **Content rail (right)** — `OptionsPanel`: a **layers list**, plus a `transition` band when a slide is active. Nothing else: general settings and the slides list both moved out. Like the inspector, the docked rail carries **no padding of its own** — its sections are full-bleed bands and must reach the rail's edges; anything that is not a section (the recording / import banners) pads itself. A `p-2` on the rail is the bug to look for when a band stops touching the edge.
- **Filmstrip** — `SlideFilmstrip`: horizontal thumbnails, dnd reorder, per-slide aspect ratio from `size` overrides. Docked: a band between the rails whose height travels through `--studio-filmstrip-height` (8rem with slides, 3rem empty, 0 otherwise) — SketchPage subtracts it from the viewport, the band sizes itself with it, the transport bar offsets above it. Floating: a card at the foot of the right column, under the content panel and the same width — with the deck there rather than over the canvas, nothing sits under the floating transport bar. The strip is `items-start`: a slide is a thumbnail plus a name line, so centring the row pushed the add button (which has none) half a line out of alignment. **The add slot is a slide, not a button** — a dashed tile the height and aspect of the slide pressing it would create (the active slide's `size`, the canvas's when the deck is empty, since a new slide inherits the active one). An empty deck is that same row with only the slot and a caption, and it carries the row's own padding: as a floating card sized by a bare pill it measured 32px tall, and a 16px radius on 32px reads as a pill beside the tall panels (66px with the padding and the slot). The docked band is 3rem when empty, so that host passes a smaller thumbnail height rather than letting the slot overflow it.

### Thumbnail tile: bigger image, one hover toolbar (2026-08-31)

`SlideThumbnail`'s three `thumbnailHeight` call sites in `SketchOptions.tsx` were 48–72px, too small for the sketch preview to read (reported via a screenshot: an all-but-illegible tile with two icon buttons stacked in the top-right corner, directly on the artwork). Now 88 (mobile drawer) / 104 (floating desktop) / 112 (docked desktop) — the docked band's hardcoded `--studio-filmstrip-height` literal moves with it, currently 8rem (mobile and floating aren't pinned to a literal — their card just wraps the content, see the ResizeObserver note on the mobile deck wrapper above). Only the docked-desktop number is load-bearing this way; changing it again means re-deriving the rem value, which is now simply `thumbnailHeight + 16px` (the strip's uniform padding, twice), not eyeballing it.

**The tile is a bare rectangle, and that is load-bearing geometry, not a style choice.** A name line under the thumbnail made the cell asymmetric and the corners impossible to reconcile — measured: 6px above the thumbnail against 26px below it (4px gap + 16px name + 6px padding), inside a card whose padding was `px-3 py-1.5`. Concentric corners need `inner = outer − inset`, so a 16px card with 6px vertical and 12px horizontal padding wants a 10px radius on one axis and 4px on the other at the same time — unsatisfiable. Both fall out of one decision: **the name lives inside the tile as a `glass` badge (top-left) and the strip uses one uniform `p-2`**, giving 8px on every side and an 8px tile radius that is genuinely concentric with the card's 16px. Verified after the change: 9.1px above and 9.1px below (the 1.1 is the active tile's `outline-offset`), card 122px tall instead of 136px. Do not reintroduce a name line under the thumbnail, and do not split the strip's padding per axis — either one breaks the corners again.

**The tile has a width floor the toolbar sets.** Tiles are sized by height, but the width follows the slide's aspect ratio — at the common 0.8 portrait ratio a 72px tile is only 58px wide, while the action toolbar (two 28px buttons + gaps + padding) is ~62px: it overflowed its own tile. Any future height reduction has to be checked against `thumbnailHeight × narrowestAspectRatio > ~62px`, or the buttons have to shrink with it. This is also why **rename is not a third toolbar icon** — three buttons measure ~92px against an 83px tile — and is triggered by clicking the name badge instead.

The name badge is also the rename affordance: clicking it swaps it for an input (Enter commits, Escape reverts, blur commits). It stops `pointerdown` propagation so renaming never starts a drag-reorder. The old always-visible pencil next to the name is gone with the name line.

The duplicate/delete buttons moved off the artwork entirely: a bottom scrim + one `glass` toolbar (same token as every other floating panel), 28px buttons (was ~16–20px, under the 44px tap-target floor). The block is `rounded-lg`, **matching the tile's own radius rather than being a pill** — at this size a `rounded-full` block read as a badge dropped onto the thumbnail instead of part of it; its buttons are `rounded-md` so they nest inside it. Both icons share one resting style — delete only turns red on its own `hover:` (`hover:bg-red-500/15 hover:text-red-500`), not permanently, which is a deliberate exception to "Visual language" below's "red is reserved for recording-in-progress": destructive-delete-on-hover already predates this change (the old tile had a permanently-red trash icon), this just scoped it to the actual hover instead of leaving it always-on. The rename pencil now follows the same `opacity-100 md:opacity-0 md:group-hover:opacity-100` reveal pattern as the toolbar rather than sitting next to the name at all times.

**Black inactive thumbnails: every capture must be slide-synchronised, and an unconfirmed uniform capture is never stored (2026-08-31, fixed).** The symptom (WEBGL p5 sketch, e.g. `kinetic/kinetic-plane`: after adding slides, inactive tiles held 1.6KB uniformly-black JPEGs, `maxLum: 0`, while the active one was correct) came from `useSlideManagement.handleSlideSelect` capturing the **outgoing** slide fire-and-forget with no index: it skipped `waitForSlideRendered` and read the canvas mid-switch. A WEBGL canvas read that is not aligned with the draw loop hands back a blank buffer — only reads chained off `waitForSlideRendered`, which resolves *inside* a rAF callback and is followed by canvas-engine `readFrame()` identity microtasks, reliably see pixels — and the blank was flattened onto `captureThumbnailFromCanvas`'s `{ alpha: false }` (black-initialised) destination into a valid-looking black JPEG, stored for good because the lazy re-capture effect in `SketchOptions` skips slides that already hold a thumbnail. The fix is three rules, all in `thumbnailUtils` / `useThumbnails` / `useSlideManagement`:
- The outgoing capture happens **before** the switch, synchronised on the *current* index, and the switch is deferred until it settles (`.then( performSwitch, performSwitch )`); the wait is bounded (`waitTimeoutMs: 350`) so a wedged canvas can only delay the switch imperceptibly, and since the switch hasn't happened yet, whatever frame it reads still belongs to the outgoing slide. Do not revert to fire-and-forget: an un-awaited capture during a switch is exactly the black-tile bug.
- `captureThumbnailFromCanvas` reports `isUniform` (every pixel identical, early-exit scan; environments without `getImageData` report `false` — fail open, since "uniform" is what discards). `captureThumbnail` stores a uniform capture **only when `waitForSlideRendered` resolved `"matched"`** — that settles the legit-black-sketch judgement call: a confirmed flat frame is an accurate tile, an unconfirmed one is a failed read and is dropped so the lazy path retries.
- After the wait, `getRenderedSlideIndex()` is re-checked: if the engine now renders a *different* slide (rapid switches, expired wait), the capture is discarded rather than stored under the wrong slide id.

**Tried and disproven: `p.setAttributes( "preserveDrawingBuffer", true )`** in the WEBGL branch of `src/sketches/p5/utils/sketch.js` (mirroring `src/sketches/threejs/utils/sketch.js`, which does need it) — rebuilt and re-measured, the thumbnails stayed byte-identically black, so this is not the p5 drawing-buffer lifetime. Do not re-apply it without new evidence.

Also fixed in passing: the active-slide outline (`outline-primary`) and the empty-thumbnail placeholder (`bg-secondary`/`text-muted-foreground`) referenced Tailwind color tokens that don't exist anywhere in `tailwind.config.ts` or `globals.css` (the app's palette is grayscale: `background`/`foreground`/`border`/`hover`/`active`/`focus`/`label`, no `primary`/`secondary`/`muted-foreground`) — those utilities were silent no-ops. Swapped for the real tokens (`outline-focus` — `--focus` is documented in `globals.css` as "ring/outline color" — `bg-hover`, `text-label`); same fix applied to the rename input's `focus:ring-primary` → `focus:ring-focus`. Worth an audit if another panel is ever found using `primary`/`secondary`/`accent`/`muted-*` — none of those are wired to a CSS variable in this app.
- **Transport bar (all layouts)** — `TransportBar`: play/pause · the scrubber (`AnimationProgressionBar variant="inline"`) · a snapshot camera · a red record dot. **It is a full-width bar along the bottom edge, not an island**: square corners, one top rule, no shadow, 3rem tall, identical in docked, floating and mobile. It became one when the floating layout had three islands competing for the bottom of the screen. Everything else is positioned off it — both docked rails and the filmstrip band stop on it, the floating islands and the mobile stack clear it by their usual margin, and `SketchPage` subtracts it from the viewport — so its height is stated once, in `--studio-transport-height` (`STUDIO_TRANSPORT_HEIGHT_VAR`, published by `SketchOptions`). **This reverses an earlier call** not to add a second height variable: that held while the bar rode inside the mobile stack, and stopped holding the moment five boxes had to line up against it. Being screen-wide, the bar also brought back readouts the pill had dropped — `frame / total · elapsed / duration · percent`, the last two hidden below `md` where only the clock fits. Snapshot and record sit together on purpose — one still, one moving image, the two ways out of the sketch; both go through `@/lib/canvasSnapshot`, which reads the engine's capture source rather than `getCanvas()` (DOM engines only refresh their mirror canvas on redraw, so a live read during playback returns a stale or blank frame) and is shared with `EngineControls`. It replaced the scrubber that used to be welded under the canvas and the capture card that floated bottom-right; **there is now exactly one scrubber in the DOM, in the transport bar**, on phone as on desktop. Because the scrubber left the viewport, SketchPage passes its `onSeekStart`/`onSeekEnd` down to `SketchOptions` — without them the viewport's performance label stops reporting "seeking".
- **Engine controls are identity, not playback** — after the transport became the bar, `EngineControls` (the top-left island, and the same buttons in the docked top bar) kept only the GitHub source link and the share/embed dialog. Play/pause and the snapshot both moved into `TransportBar`, where the scrubber they belong with already was; the dev **double-click that writes the sketch's catalogue thumbnail** (1x + 2x through `/api/dev/thumbnails/save-from-canvas`) moved with the camera into `SnapshotButton` — that is where to look when a thumbnail needs regenerating. Removing a control from that row means checking the new last child for an orphaned `border-r`: it has now bitten twice, on the camera and on the share trigger.
- **Capture is one dialog, several triggers** — `CaptureDialog` holds the export panel + `CaptureActions`. It carries **no options import/export**: moving a sketch's JSON is a document concern and lives in the content rail's own section (`OptionsPanel`), not in an export surface — an "Export" button inside the Export dialog that exported something else was the confusion worth removing. The record dot opens it, and in the docked layout so does the top bar's Export button (the only solid, ink-filled button on screen). **Its content stays mounted while closed** (visibility toggle, plus `pointer-events-none` on the closed container so it never eats clicks over the sketch): `captureActionsRef` is the autosave handle (`useFormState` calls `saveAsDraft` through it) and a running recording must survive the dialog being dismissed. Undo/redo sits beside Export; both portal from `SketchOptions` into a `DockedTopBar` slot (`actionsSlotRef`) because the bar belongs to SketchPage while these need the form context — same pattern as the zoom-controls slot.
- **The bottom stack is derived, not hard-coded** — the transport bar is the floor, then the filmstrip band, then the floating islands and the Interactive mixer, each offset computed from the one below (`transportHeight` → `railBottom` / `islandBottom` → `mixerBottom` in `SketchOptions`). Adding a layer means inserting one term, never re-tuning three magic numbers.
- **Floating mode is kept**, reorganised not removed: same panels as islands, capture card stays in the bottom-right stack (no top bar to host Export there). The maintainer plans draggable floating panels later — panels must not hard-code their own anchoring; the wrapper/container owns position.
- **Global single-key shortcuts go through `useGlobalHotkey`** (`src/hooks/useGlobalHotkey.ts`, 2026-08-31): Space toggles play/pause (`TransportBar`), E opens the capture/export dialog (`SketchOptions`' `openCapture`, the same trigger the record dot and the docked Export button use), S opens the share/embed dialog (`SketchShareDialog`'s `openShare`), F toggles fullscreen (`SketchPage`'s `toggleFullscreen` — enters the "keep UI" `hud` mode, since "Fill screen" `bare` stays a deliberate menu-only choice). Every caller registers a `window` `keydown` listener, not scoped to any DOM subtree, since the control a shortcut drives is rarely what has focus. The hook backs off wherever the key already has a job — text entry (`isContentEditable` + `input`/`textarea`/`select`), anything a button/link/ARIA-control role covers (so a focused control's own click-on-Space/Enter doesn't also fire the shortcut — the play button is the concrete case), and anywhere inside an open `role="dialog"`/`aria-modal` (`CaptureDialog`, `SketchShareDialog`) — via one shared `INTERACTIVE_SELECTOR`, so a new Space/E/S/F-sensitive control is extended there once rather than copied per caller. Also ignores Cmd/Ctrl/Alt combinations and `event.repeat` (holding the key down triggers once). E/S only open (pressing again while already open is a no-op); F is the one that toggles, matching Esc already closing fullscreen. Known gap, accepted rather than solved: the dialog-open guard is target-based (closest() from whatever has DOM focus), so a shortcut can still leak through to a control underneath an open dialog if focus never landed inside it.
- **Mobile** — **two floating cards riding on the transport bar**, the desktop floating layout stacked instead of spread over two columns: a wrapper (`absolute left-2 right-2`, bottom offset by the transport variable, `flex flex-col gap-2`) holds the deck card and the collapsible drawer. The deck is a card of its own and not the first row of the drawer's body — it is navigation, so changing slide must not mean opening the settings drawer, nor scrolling the panel that holds them; it reaches the drawer as a `deck` node. Two tabs only, Sketch (canvas & animation + sketch form) and Content. **Recording and export are not a tab**: the transport's record dot opens `CaptureDialog` as a bottom sheet — the same single surface the desktop uses, so nothing about capture is duplicated per layout, and the mobile drawer no longer statically imports `CaptureActions`/`OptionsImportExport` (it also stopped re-rendering on every keystroke, since `capture.options` was `methods.watch()`). The engine-controls red-dot shortcut and its `OPEN_EXPORT_DRAWER_EVENT` are gone with it. Its tab bodies carry **no horizontal padding**, same rule as the docked rails — the sections are full-bleed bands, and the banners pad themselves. The Sketch tab opens with "canvas & animation" **collapsed** on mobile only (`useCollapsibleStates( isDesktop ? undefined : { rootSettings: false } )`): the drawer scrolls inside `max-h-[50svh]`, where two unfolded sections pushed the option count several screens down. **The wrapper — deck plus drawer, the transport excluded since it has its own variable — is what `--studio-drawer-height` measures, in both states**: it is observed collapsed too, where the old drawer published `0` and let the canvas run under the pill. The wrapper must hug its content (no `h-full`, no `inset`) or it becomes an invisible pointer trap over the sketch.

## The content rail is a layers list, not a stack of forms

2026-08-31 — One band, `layers`, holding two labelled groups of the same list: **this slide** first (what you edit most) then **shared by all slides**. Both are live — a shared layer is edited here like any other, and the group label is what says it applies everywhere. Decided against the mockup's third state (shared rows greyed with a lock, "hérité", clicking one jumping you to another scope): a mode to learn for no gain.

- **A row selects; the list is replaced by the layer's inspector.** `ContentLayers` ⇄ `ContentLayerDetail` in the same band, with a back arrow — one panel, and mobile behaves identically. The old shape stacked every item as an accordion, so opening one pushed the rest off screen and the composition was never visible at a glance.
- **Selection is one channel, shared with the canvas.** `ContentSelectionProvider.selectPath` already existed to bridge `CONTENT_ITEM_SELECT_EVENT` (dispatched by `contentDrag.js` when you press an object on the sketch); the list calls the same function, so pressing an object and pressing its row open the very same inspector. `selectPath( null )` is the back action. Verified by dispatching the event with `index: 1` and landing on the second layer's form.
- **Layers have no name in the data** — `ContentItemSchema` is a discriminated union on `type` and nothing else identifies an item, and the model was explicitly out of scope. `describeContentItem` (the only place that names a layer) derives the type's label from `ITEM_META` plus a preview of whatever the item carries that a person recognises it by: the text it prints, the image's basename, a stack's count. Add a kind → give it a preview there.
- **The palette hides behind a `+`**, unfolding under the header it belongs to. One `+` per group rather than one for the panel: with two scopes on screen a single add button cannot say where the layer would land. **A group names itself only when there is another group to tell it apart from** — without slides the single group drops its header entirely and its `+` moves into the band's own (`PanelSection actions`), because otherwise the panel printed "layers" twice, once as the band and once as the group, with the same count under it. That band `+` also opens the band when it is shut, so the palette never unfolds out of sight.
- Every band in the rail must be collapsible: `transition` shipped with a hard-coded `expanded` and no `onToggle`, so it could not be shut. It has its own `CollapsibleStates` key now — a `PanelSection` without an `onToggle` is the bug to look for.
- **A slide group must be keyed by its path.** `useFieldArray` keeps its `fields` when only `name` changes, so without `key={ `slides.N.content` }` on the group's providers, switching slides left the previous slide's rows on screen bound to dead paths — they rendered as a nameless "Layer". The `SlideEditor` this replaced remounted via `key={ editorKey }` for exactly this reason; the lesson survives the component.
- **The split is where the weight is**: `ContentLayers` (rows, icons, dnd-kit) mounts with the band, `ContentLayerDetail` (`GenericItemForm` → `FieldRenderer` → every `Controlled*` input) is its own `dynamic()` and compiles only when a layer is opened. That is why the band can now default to open where `globalContent` had to default closed.
- Retired with the old shape: `ContentItems`' list component, `SlideEditor`, `ItemFormWrapper` (and with it the scroll-into-view + `animate-select-pulse` reveal — the selection opens the inspector outright now) and `AddItemControls`. `SortableRow`/`DragBinder` moved out to `components/SortableRow.tsx`, since the filmstrip and the slide thumbnails share it.

## The selected slide is named once, by the filmstrip

2026-08-29 (name moved inside the tile 2026-08-31, see the thumbnail entry above — it is a badge on the thumbnail now, not a line under it; the rule below is unchanged) — The highlighted thumbnail is the only place the selection is named. Panels never repeat it: the inspector header is just "Controls", the content rail's section is "content" (vs "shared content"), and `SlideEditor` renders no caption of its own. Before this, one screen carried the name four times — `Controls · slide 2`, a `SLIDE 2 CONTENT` section, a raw `root.slides[1].content` line inside it (0-based, 30px under a 1-based header), and the thumbnail — which on mobile made two *tabs* claim the same object while the Sketch tab, editing `slides.N.*`, carried no marker at all. **The one exception is deliberate**: `SketchBreadcrumb` keeps ` · slide N` over the canvas, because it names what is *rendered*, not what is edited. **How to apply**: if a panel needs to say which slide it edits, the answer is that the filmstrip must be visible, not that the panel should print the name.

## The export dialog is a table, one row per variant

2026-08-29 — `CaptureDialog` holds `ExportPanel`: a table where each row is an export variant and every setting is editable in place — size, output file, frame rate, slides, delivery. Rules that are load-bearing rather than cosmetic:

- **The batch IS the table, and the row IS the queue item.** A first attempt split a variant list beside an editor for the selected one; it showed one variant's settings and summarised the rest, which is the wrong shape for a tool whose job is producing several outputs at once. It also stated every spec twice. Rejected — do not reintroduce a selected-variant editor panel.
- **A column that does not apply says so with a dash**, never a control that would be ignored: no frame rate for a still, no slide scope without slides, no delivery choice for a single file. Most of these settings are conditional and the UI must honour that — it is what keeps the surface calm.
- **"Kind" is not a control.** The Output column lists what you get — `mp4` / `webm` / `gif` / `png (still)` / `png × 10 · 20 · all` — and `variant.kind` is derived from it. Asking for a kind and then a format inside it made the user say the same thing twice.
- **The size picker is the sketch form's own `formatOptions`** (`RootSettings/constants/root-field-config.ts`), not a second list — a hand-maintained copy would drift the first time someone adds a preset. Fullscreen sentinels are filtered out (they drive the Fullscreen API, not a W×H, so they are meaningless as an export target), and a `Custom…` entry swaps the cell for width/height inputs.
- **`null` means "follow the sketch", and `makeVariant` must never resolve it.** A variant's `size` and `framerate` are nullable; the table and the runner both read null as the sketch's own value. `makeVariant` therefore takes only a preset and reads no options at all — resolving those to concrete numbers at creation is what froze the seeded default at whatever the canvas and framerate happened to be when the list was first built, so it stopped tracking the sketch afterwards. A preset that names a size still pins it; that is what picking "Reel" means.
- **Choosing the sketch's own value stores `null`, not that value.** `<select>` cannot carry `null`, so a column offering only concrete numbers would pin on the first interaction and never go back — and since variants persist to `localStorage`, that pin outlives the session with nothing able to undo it. The way out is *not* a separate "Sketch's own" entry: it was tried, and a label repeating a number the row already shows was rejected as wasted width (the rate column truncated it). Instead the cell selects the sketch's own value among the ordinary options, and `onChange` maps that value back to `null`. A sketch sized outside the preset table gets its dimensions appended as one extra option, so it stays selectable. The cost, accepted: a followed 60 and a 60 pinned by hand look identical — they behave identically too, until the sketch changes.
- **Reconciling mixed slide sizes lives in the size cell**, not in a warning bolted to delivery: when a variant follows the sketch's own size and its slides disagree, "Sketch's own" splits into smallest / biggest / root canvas. It is a size decision, so it belongs in the size control.
- **`[+] Add a variant` opens a preset menu** (Reel · post · square · 16:9 · current canvas · still), never a blank row. A first-time list is seeded with one "current canvas" variant, so opening Export and pressing the button reproduces what the old single-shot recorder did.
- **One ink-filled button**, bottom right, becoming a bordered red `Stop` while running — red stays reserved for capture in progress.
- **The glass belongs to the dialog's chrome, not to its content.** `glass` is `bg-background/80` plus a blur, which is right for a title bar and a footer floating over the canvas and unreadable behind a table of small mono values. The scrolling table region therefore sets an opaque `bg-background` of its own; measured, the region reads alpha 1 while the dialog shell stays at 0.8.
- **Mobile** keeps Export appearing exactly once, as the same dialog. The table holds a `min-w-[600px]` floor and the container scrolls sideways: crushing six editable columns into a phone reads worse than a scroll. A card fallback for narrow widths is still open.
- **The preview takes the table's place, it does not stack on it.** A finished row's Delivers cell becomes a `✓ <size>` button that swaps the scrolling region for `ExportPreview` (players, a filename+size caption, Back, and one primary Share/Download action). A second modal was rejected: the dialog is already a bottom sheet on mobile, and a surface over a sheet fights the chrome instead of using it. The preview dies with the dialog by design — `ExportPanel` is mounted only while it is open, so the blobs and their object URLs are released on close and a new run clears the last one's.

Variants live in a module singleton persisted to `localStorage` per sketch (`src/lib/export/variantStore.ts`), deliberately **not** in the options form: they are a rendering queue, not part of the document, and putting them in `OptionsSchema` would push them into every persisted job, every `/embed` link and the options import/export JSON, and fire the form's 400ms undo/redo auto-capture on every tweak.

## "Document" is not a scope in the UI

2026-08-28 — With at least one slide, the selected slide is always what is edited; without slides, the root blocks are. This matches what the code already did (`effectiveActiveIndex` falls back to 0; `resolveEffectiveSketch` spreads `slide.sketch` over root `sketch`, so the root is never *read* once a slide covers it) and the maintainer's history: slides were added after the fact, root `sketch` is the defaults holder, and slides are expected to grow into a preset system (a slide ≈ a named variant). Consequences, all deliberate:
- **No Document/Slide scope switcher** and no "Doc" card in the filmstrip — both were mocked up and rejected as a third state nothing needs.
- **Rejected: blue override indicators / per-field link-to-document chains.** Mocked, then dropped: `ControlChrome`'s existing modified-state (label gains weight, per-field reset appears) is the only signal wanted. Do not reintroduce colour-coded override badges.
- **The 0 ↔ 1 slide boundary must be lossless** (`useSlideManagement`): deleting the last slide demotes everything (sketch, size, animation, content appended after root's, asset lists unioned, interactive merged slide-wins); adding a slide inherits the active slide's current settings, never `sketchFormValues` factory defaults; everything handed to `makeDefaultSlide` is deepCloned because `SlideSchema`'s `sketch: z.any()` passes references through (the first slide used to alias the root sketch object).
- Open: root `content` ("shared content") is editable in place in the rail; the maintainer may later want propagation via apply-to-all instead.

## Filmstrip ≠ timeline

2026-08-28 — Slides are a collection of variants, not a temporal sequence; a slide is on its way to being a preset. The filmstrip therefore stays a separate band from the `AnimationProgressionBar` scrubber. Rejected: merging them into one bar where each slide is a timeline segment — it would impose sequence semantics the model doesn't have.

## Dev actions are hidden behind a menu toggle

2026-08-29 — The studio's dev-only affordances are gated on `useDevActions()` (`src/hooks/useDevActions.ts`) and **off by default**, toggled by "Display dev actions" in the burger menu. They used to be gated on `NODE_ENV === "development"` alone, which meant they were permanently on in the only environment the maintainer works in: demo screenshots needed cropping and the studio never read as the shipped product.

Seven affordances across four hosts, all now behind the flag: the pending red badge and the Debug/Pending sections in `MenuBar`, the save-defaults / thumbnail / preview trio and its divider in `SketchSettings`' action bar, the `DevPreviewButton` in the export dialog, and the camera's save-as-thumbnail double-click in `SnapshotButton` (inside the transport bar). **Nothing moved** — relocating them into the menu was considered and rejected, because it churns two panels and the preview recorder is entangled with `useBrowserRecorder` + `recorderCapabilities`, and a per-sketch `/debug` route was rejected because `SaveDefaultsButton` calls `getValues`/`reset` and must stay under the `FormProvider`.

Three things to keep right when touching this:

- **The build gate lives on the read, not on the store.** The preference is an ordinary persisted boolean; `devActionsVisible` is `IS_DEV && preference`. Putting the `NODE_ENV` check inside the setter instead makes the store untestable under Jest (which runs `NODE_ENV=test`) while giving no extra safety — a stale `true` still cannot surface dev UI, because the gate is on the way out.
- **The pending badge was the worst offender and is the easiest to miss**: it is *not* `IS_DEV`-gated in `MenuBar`, only indirectly false in production because `hasMissingThumbnails` / `hasMissingPreviews` come from `layout.tsx` as `false`. Reading the component alone gives no hint it is dev-only.
- **The camera's 250ms deferral is on the production path.** In dev the plain download was delayed so a double-click could beat it; with the flag off that delay must be gone, or a screenshot-clean studio still behaves differently from the shipped one. That state machine lives in `SnapshotButton`, not `EngineControls` — it moved with the camera into the transport bar.

`useSketchDevWatch` stays out of it — no UI, and it is the sketch hot-reload. No server change either: every `/api/dev/*` route already 404s in production independently of the client gate.

## Panel sections: bands, not boxes

2026-08-28 — Every settings group is a `PanelSection`: a full-bleed header (uppercase, letter-spaced eyebrow + optional meta/actions + chevron) closed by a hairline running edge to edge. Sections read as a stack of bands, which keeps a long inspector scannable without boxing each group in its own card. The rule does the structural work — do not re-add per-section borders, rounded cards or background tints.

Depth is expressed by *treatment*, not by nesting boxes (`FieldRenderer`'s `nested-object` takes a `depth` prop, threaded from `GenericObjectForm`): depth 0 — a group directly under a section — renders as a sub-band with its own top hairline and a full-bleed, hover-highlighted header; deeper groups get a left indent guide and no rule. The previous style put every group in a `border rounded-xl` box with `ml-2`, which stacked borders inside borders as soon as a sketch nested two levels.

**"Band" means any collapsible group of fields, not just `nested-object`.** `item-list` (a photo/asset collection with its own add/remove/reorder — e.g. `photo-stamp-collage`'s "Photos") is a group too, just a homogeneous one, and was left out of `GenericObjectForm`'s `BAND_COMPONENTS` set the first time this rule was written (2026-08-31, `photo-stamp-collage`: "Photos (8 items)" sat visibly shorter and in a different, hard-coded `text-gray-500` next to sibling `nested-object` groups in `text-label` at `py-2 md:py-1.5` — same defect, two symptoms). Any component that owns a `CollapsibleItem` header at depth 0 belongs in that set: it must self-pad with `leafPaddingClassName` exactly like `nested-object` does (header **and** body, both axes), because `GenericObjectForm` skips its own padding wrapper for anything in `BAND_COMPONENTS` — half-applying the set (matching the header but not the body, or vice versa) reproduces the doubled- or missing-padding bug this section exists to prevent.

**A translucent parent needs an opaque child to show a border, not just a background.** `item-list`'s box is `bg-background/50` over the panel's own `bg-background`; its rows were `bg-background` with no border of its own (2026-08-31, `photo-stamp-collage`'s "Photos"), which computes to the *same* opaque white as the translucent box over that same backdrop — rows and box were indistinguishable, and consecutive rows only had a 4px `space-y-1` gap between them, no divider. Fixed by giving each row `border border-theme` — the same border the list's own sibling "Add Item" button already carried, which is what made the missing one on the rows above it obvious.

**An item-list row's drag handle and delete button must be `items-start`, sized to the row's own header, never `items-center` on the whole card.** `itemConfig` can be anything — a one-line control bar, or (`photo-stamp-collage`'s "Photos") a `nested-object` that expands into a tall form. `items-center` on `SortableItem`'s flex row centres both buttons on the *card's total height*, so an expanded item floats its drag handle and trash icon at the vertical middle of the whole form instead of beside the row that owns them (2026-08-31). Fixed with `items-start` plus giving both buttons the same padding family as the header's own action icons (`p-2 md:p-1.5`, `rounded-md`, `hover:bg-hover`) rather than a bespoke size — that alone lands them on the header chevron's own center, collapsed or expanded, without hard-coding a height to any one `itemConfig` shape.

**An item's own field renders at `depth + 1`, never at the default 0.** `SortableItem` called `FieldRenderer` without a `depth`, so a `nested-object` `itemConfig` took the depth-0 **band** treatment — `py-2 md:py-1.5` plus a self-applied `leafPaddingClassName` — which is sized for a group spanning a `PanelSection`, not one sitting inside a bordered `p-1` item card that already owns its edges. The result was a collapsed row visibly taller than its own drag/delete buttons with horizontal padding it had no use for (measured 2026-08-31, `photo-stamp-collage`: header padding `6px 12px` → `4px 0px`, row 44px → 40px desktop, 56px → 52px mobile once depth was threaded). `ItemListRenderer` takes its own `depth` from `FieldRenderer` and hands `SortableItem` that value; `SortableItem` passes `depth + 1` down. Leaf `itemConfig` types never read `depth` (only the `nested-object` and `item-list` cases do), so threading it is free for them.

Two traps, both hit on the first attempt and both structural:

- **Padding lives on the leaves, never clawed back with negative margins.** A band cannot reach the panel edges with `-mx-3` — measured, it landed 25px short of a 320px rail, because the margin is relative to `FieldRenderer`'s own wrapper, not the panel's content box (the scrollbar and the section padding both intervene). So `PanelSection` takes a `bodyPaddingClassName` (`px-0` for form bodies) and `GenericObjectForm` applies `leafPaddingClassName` to leaf fields only; groups render unpadded and pad their own header and children. Bands then span edge to edge by construction.
- **A section never pads its own body when the content ends in a band.** `PanelSection`'s default `pb-3` shows up as dead space between a trailing collapsed band and the section's hairline, so form bodies pass their own `bodyPaddingClassName` (both axes) and `GenericObjectForm` adds the trailing space only when the last field is a leaf. Same principle as the horizontal padding: full-bleed content owns its edges.
- **Spacing between bands comes from the band, never from a container `gap`.** A `gap` on the fields container also pushes the bands apart, leaving each separator floating in dead space instead of reading as the top edge of the group it introduces. The container has no gap: leaf wrappers carry their own `py`, bands sit flush against their hairline (measured: 0px between consecutive band roots). For the same reason a band header carries no hover tint — the rule and the chevron already say it is interactive, and a tinted row reads as a selected item.
- **A rule marks every boundary a band takes part in** — above a band, and above the plain field that follows one; two plain fields in a row are a list and get none. `GenericObjectForm` decides this from the field's neighbours and draws it on an outer, unpadded wrapper, so the rule spans the panel even when the field inside is padded.
- **`first:`/`last:` variants cannot pick out a group.** Every `FieldRenderer` return is wrapped in its own `<div>`, so each group is always `:first-child` — a `first:border-t-0` silently removed *every* rule (`borderTopWidth` measured `0px` on all of them). Position is computed in the parent form instead. Assume the same about any positional variant inside this form tree.

Order inside the inspector: **canvas & animation first, then the sketch's own parameters titled "N options"**. The count used to sit in the panel header, where it described only part of what the panel held; it now titles the block it actually counts, and the header names the surface instead ("Controls" + the active slide).

## Collapse animations: never animate width or radius

2026-08-28 — **The floating panels do not collapse as a whole any more** — only their sections do, so the section titles stay on screen and a fully collapsed panel is already a compact stack of headers (measured: 320px wide, shrinking from 532px to 385px with one section closed). That removed the second, competing toggle on the inspector and the content card, and with it the morph below.

The floating inspector and the Interactive mixer used to swap `w-80` ↔ `w-fit` and `rounded-2xl` ↔ `rounded-full` between states. Neither is animatable (auto width has no interpolation), so the panel snapped into a pill while its height was still interpolating through `CollapsibleItem`'s `grid-template-rows` transition — a visible morph. Both now keep a **constant width and radius**; only the body height animates. **How to apply**: a collapsible floating panel picks one width and one radius for both states. Verified by sampling the box through a collapse — 320px / 16px constant, height 532 → 34. Sampling *intermediate* heights headlessly is not possible here: SwiftShader renders a sketch page at ~2fps, so a 200ms transition completes between two animation frames and every poll lands on an endpoint.

## One radius for every floating surface

2026-08-30 — All of them are `rounded-2xl` — 16px, measured: the inspector, the content rail, the deck card, the transport bar, the capture dialog and the mobile drawer (which was `rounded-xl`). When a short panel *looks* rounder than a tall one the radius is not the cause: it is a panel with no padding of its own, whose height collapses onto its content until 16px covers most of it. **Fix the padding, never the radius** — a per-panel radius is what makes a stack of islands look assembled from parts.

## Visual language (from the validated mockup)

2026-08-28 — Monochrome stays the rule: the Export button is an ink-filled pill precisely because nothing else is filled; red is reserved for recording-in-progress (the mobile record shortcut already uses it). The sketch name appears once — the breadcrumb above the canvas — never in the top bar. The full zoom cluster (−, %, +, 100%, fit/fullscreen) survives in the docked bar; do not collapse it to a single fit control.

## HUD elements are standalone content-item types

2026-08-31 — The single `hud` content item (one slot per telemetry widget, shared style, `enabled` per slot) is gone: each widget is its own item type — `hud-badge`, `hud-gauge`, `hud-sparkline`, `hud-counter`, `hud-crosshairs`, `hud-swatch`, `hud-bounding-box` — because one-per-kind was the container's hard limit (two counters meant two full "HUD" layers), and every such layer read as an opaque "HUD" row in the rail. Decided with the maintainer; labels stay unprefixed ("Badge", "Gauge"), discriminants are prefixed so seven generic words aren't confiscated. Consequences and rules:

- **Each element owns its full style** (`fill`/`font`/`blend`, plus the `background*` panel trio on the boxed five — crosshairs and bounding-box draw no panel and deliberately have no background fields). The container's inheritance is replaced by a context-menu entry: right-click a style field on a HUD layer → "Apply … to all HUD layers" (`utils/applyToAllHudLayers.ts`, wired in `FieldRenderer`'s existing `FieldContextMenu`, which is now composable and no longer opens only in multi-slide contexts).
- **Z-order among HUD elements is content-array order**, like every other item — the container used to force boundingBox lowest → badge top (`WIDGET_ORDER`); reordering layers now reorders the stacking, which is a feature.
- **`enabled` survives on all seven and defaults to `true`** (a layer added from the palette must show up). It powers the layers-list eye toggle (`LayerRow`): only items with a top-level boolean `enabled` get the eye; a hidden layer keeps its `EyeOff` visible without hover and dims its label.
- **Legacy `{type:"hud"}` migrates lazily on read, never in storage** — `src/utils/migrateLegacyHudItems.ts`, run in exactly two places: inside `initOptions` **before** the zod parse (an unknown content `type` fails the strictly-parsed union and the top-level `.catch` resets the whole options — the hazard `durationBoundary.test.ts` documents), and in `src/app/sketches/[engine]/[...sketch]/page.tsx` before the provider gets the object, because the engine's first render and headless recording read those options **without** `initOptions` (they only pass through it later, in the form layer). Expansion rule: a slot becomes an item iff it was enabled or its config (ignoring `enabled`) differs from its parsed defaults — a pristine container yields exactly gauge + sparkline (what it visibly rendered), a merely switched-off slot is dropped. `/embed` needs nothing: its `#o=` hash carries only `sketch` deltas, never content items.
- The on-canvas drag lost its HUD special case: the five offset-anchored types are `OFFSET_DRAGGABLE_TYPES` in `contentDrag.js` and a drag writes `item.offset` (vs `item.position`) via one `dragField(type)` switch; the `part` sub-item plumbing (`reportItemPartBounds`, `scope:index:part` keys, the `nested-…` section expansion in `useContentItemSelection`) is deleted.
- `keyPaths.js` `SKIP_TOP_LEVEL` still contains `"hud"` — that is an unrelated *sketch-parameter* key some sketches declare (`signals-01-serpent`), not the content item; leave it.
- **HUD quick-add from a control** (2026-08-31, shipped): right-click a sketch parameter → "Add a counter/gauge/sparkline for …" (numeric controls) or "Add a swatch for …" (colour), via `utils/hudQuickAdd.ts` + `makeDefaultItem`'s `seed` parameter. The element lands in the control's own scope with `source` pre-bound (`toSketchRelativePath`), a gauge/sparkline inherits the slider's `min`/`max`, and the new layer's inspector opens through the same `CONTENT_ITEM_SELECT_EVENT` an on-canvas press uses. `vector2d` controls deliberately get no entry: crosshairs consumes canvas-pixel points while sketch vectors are normalized 0..1 — the reticle would pin near the origin. Adding a kind to the menu = one branch in `hudQuickAddKinds`.

## The add-palette is a popover, not an inline unfold

2026-08-31 — The `+` buttons (per group header, and the band header when the single group is unlabelled) open `AddLayerPopover` (Headless UI `Popover`, `anchor="bottom end"`, portalled per the `BindingAffordance` precedent so the scrollable rail never clips it) containing `ItemPalette` sectioned by `ITEM_GROUPS` ("Content" / "HUD / telemetry"). The inline `CollapsibleItem` unfold was retired with the split: seventeen tiles in the panel body pushed the rows off screen. The band `+` appends to root content through `setValue("content", […])` — RHF ^7.83 propagates that to the group's `useFieldArray` — and still opens a shut band first, so the new row lands in sight.

## HUD source picker: grouped by parent key-path

2026-08-30 — The HUD elements' "Source" select (`ControlledSourceSelect`) lists the sketch's scalar key-paths, which grow fast and read as a flat wall of `colors.text` / `colors.background` / `magnitude.start`. They are now split into one `<optgroup>` per parent path — group "colors", option "text" — by `groupKeyPaths` in `@/p5/utils/hud/keyPaths` (root scalars stay together under "Sketch parameters", built-ins keep their own group). **Only the presentation is grouped**: the option `value`, the stored setting and everything the runtime resolves stay the full dotted path, and the collapsed bar still shows it so two same-named leaves are distinguishable. A nested key groups under its whole parent (`grid.cell.size` → group "grid.cell"), so the dropdown mirrors the settings tree rather than inventing a two-level hierarchy.

## Breakdown key lists are pickers, not free text

2026-08-30 — `snapKeys` and `excludeKeys` on the breakdown item are `item-list`s of `key-select` (`ControlledKeySelect`), not of `text`: typing a key blind against a sketch's parameter tree is how they got misspelled. The picker derives its options exactly like `ControlledSourceSelect` (`flattenKeys` over the form's `sketch` value, grouped by parent path with `groupKeyPaths`) but drops the live built-in sources — a key list addresses sketch parameters only — and adds a **"Whole groups"** optgroup from `collectBranchPaths`, because a group path is a legal entry (see `sketches.md`, `slides/keyMatch.js`). A value the current settings no longer carry stays selected through a `hidden` option, so an older config (or the `"seed"` default, matched by leaf name) is never silently rewritten by opening the form. Both pickers watch the **root** `sketch`, not the active slide's — the shape is the same, and the root is the defaults holder.
