## Signing in from a static site (2026-11-26)

Sketchbook has no server in production (`deployment.md`), so it is a PUBLIC Sésame client: code + PKCE, the code exchanged by the tab (`session.ts`, `oauth4webapi` — panva, certified; never hand-written). Sésame allows the token endpoint cross-origin only from the origin of a public app's redirect address (its `clientBasedCORS`), so the redirect `https://p5.steeve.website/auth/sesame` (and `http://localhost:3000/auth/sesame` for dev) must be registered on the `sketchbook` app exactly. **Three things the flow needs or it silently gets the wrong token**: `resource=https://stockage.steeve.website` on the authorization request AND on every token request (code and each refresh — without it Sésame hands back its opaque `/me` token); scope `stockage` (the API's name); `offline_access` + `prompt=consent` for a refresh token. The session (`sketchbook.sesame.v1`: tokens, `sub`, name) sits in localStorage beside the Postiz key. **Trap avoided**: the refresh token ROTATES and a reused one makes oidc-provider revoke the grant, so two tabs refreshing at once would sign the person out — refreshing runs under a Web Lock and re-reads storage inside it. A refused refresh (`ResponseBodyError`) signs out here; Sign out revokes the refresh token, Sésame's own session stays.

## What syncs, and the two rules (2026-11-26)

`plan.ts` (pure, tested) decides; `sync.ts` moves bytes; `useStockage.ts` drives it. **Pieces**: one store document per gallery entry (kind `piece`, the entry minus its thumbnail, `summary = { sketch, at, hash }`), the thumbnail a file by SHA-256. Each side is compared with what the last sync knew (`sketchbook.stockage.v1`: per person, id → revision + hash), which is what tells «deleted here» from «new there»: here-only + known → deleted there → delete here; there-only + known → delete there; both changed → the store wins (only a rename or a mark can change; a document change is a new piece). Pulling past the 500 cap prunes the oldest here, and the next sync deletes them there: the cloud keeps the same 500. **Settings**: ONE document (`settings`) of `collectCarried` stores (never the key), merged three ways against the last sync's agreement: record stores (sends, readings, campaigns) are the union (`mergeOne`); a whole-value store (the Plan, Results, an export list, the Postiz connection) takes the store's value unless it changed HERE since the last sync. A browser's FIRST sync takes the store's whole values over its own (resuming elsewhere means finding the work as the other device left it). `writeCarried` writes the merge as decided, keeping this browser's Postiz key; with none, the connection waits as `sketchbook.postiz.pending.v1` for Publishing (`carry.ts`).

## When it runs, and the reload (2026-11-26)

`useStockageSync` is called by `MenuBar` itself, mounted on every page — NOT by the menu's lines, which exist only while the menu is open (the trap `PublishingPeek` documents). It syncs when a page opens, 4 s after a gallery change, when the tab is hidden, every 5 min while visible, and on a click of Cloud; one sync per tab, and across tabs under a Web Lock. Every store keeps a copy in memory, so settings written by a sync only show after a reload: the opening sync reloads ONCE per tab session (`sessionStorage` guard); a later one says «click Cloud to reload». Pieces need no reload (the gallery store notifies). Behind `NEXT_PUBLIC_STOCKAGE` (off): nothing is drawn or fetched until it is on.
