# Architecture

Read before touching the engine abstraction, feature flags, the Next config or anything about what ends up in which bundle.

## Rendering is engine-agnostic on purpose

2026-08-20 — Every rendering back-end implements one interface, `SketchEngine` in `src/engines/types.ts`, and the studio route and the recording pipeline only ever talk to that interface. p5.js, GSAP and Three.js are peers, not a primary plus experiments. The contract covers lifecycle (`init` / `destroy`), playback, a typed event map (`ready`, `frame`, `complete`, `error`, `performance`) and deterministic capture. **How to apply**: adding a rendering back-end means implementing `SketchEngine` and registering it in `src/engines/registry.ts` — never special-casing an engine inside the studio page or the recorder. Read `types.ts` before anything else in this area; it is the file the rest of the system is written against.

## Cavalry renders through a vendored WASM runtime that is deliberately not committed

2026-09-02 — A Cavalry sketch is a user-supplied `.cv` scene, not code, and it renders through Cavalry's **Web Player** — a self-hosted WebAssembly runtime that is not on npm and is **not** committed (multi-megabyte, and `/public/assets/libraries` is gitignored). It is downloaded from Cavalry into `public/assets/libraries/cavalry/`; only the README there is force-added, so the folder documents its own install. Without it `loadCavalryPlayer()` throws and the engine shows a placeholder while the editor and upload stay usable — so a fresh clone is never broken, just not rendering. The documented flow, which `player/loadPlayer.ts` implements, is `CavalryWasm({canvas, locateFile})` → `Module.FS.writeFile("scene.cv", bytes)` → `Module.Cavalry.MakeWithPath("scene.cv")` → `Module.makeWebGLSurfaceFromElement(canvas, w, h)` → `player.setFrame(n)` / `player.render(surface)`, with `getStartFrame()` / `getEndFrame()` / `getFPS()` for the range. **How to apply**: two traps. (1) A composition carries an `inTime`, so its range is routinely **not** zero-based — map app progress across `[getStartFrame(), getEndFrame()]`, never `progress * frameCount`, or you render the wrong part of the scene or nothing. (2) Do **not** use the runtime's own playback; the engine owns a rAF loop that pushes frames through the same `setFrame` → `render` path the recorder uses, otherwise a second wall-clock timeline fights the app's duration/framerate and preview diverges from export. The runtime is loaded with a `new Function( "url", "return import( url )" )` dynamic import so neither webpack nor Turbopack tries to resolve a `/public` asset at build time. The API is in **beta**: the loader probes for these names and throws naming what it found rather than silently rendering nothing. Cavalry's own domains are blocked by the sandbox's egress proxy, so the integration was verified against a stand-in module implementing that surface — the same trick works for any future change here.

## Every engine needs a `destroyed` flag re-checked after every `await`

2026-08-31 — React strict mode (dev) mounts `EngineSketchRenderer`, destroys it and re-mounts it synchronously, so a destroyed engine's still-pending `init()` resumes *alongside* its replacement's and appends a second canvas to the shared container — two stacked players, doubled handlers, capture reading the dead one. `P5Engine`, `GsapEngine` and `ThreeEngine` each carry a `private destroyed = false`, set in `destroy()` and re-checked with an early `return` after **every** `await` in `init()`. **How to apply**: a new engine must do the same from the start — this is not optional boilerplate, and `CavalryEngine` shipped the bug before it was added. Clearing stale canvases at the top of `init()` does **not** fix it: both inits get past that clear before either appends. Guard the append sites too (a helper called after awaits), and when the runtime mounts its own canvas, `dispose()` it on the destroyed path rather than just returning. Reproduce with the dev server (never a production build — strict mode is dev-only) and count `.sketch-canvas-container canvas`: 2 is the bug, 1 is correct.

## Deterministic capture is a design constraint, not a feature

2026-08-20 — The same sketch must produce the same frames in the live preview and in headless capture, otherwise a recording does not match what the user tweaked. That is why the engine interface exposes `beginDeterministicCapture` / `seekAndDraw` / `captureFrame` (`src/engines/recording/`) and why sketches receive a duration-scaled loop clock rather than raw elapsed time. **How to apply**: never drive a sketch's animation from `Date.now()`, `millis()` or frame counters — take the `time` argument. A sketch that reads wall-clock time renders correctly in the browser and wrongly in an export, and nothing in CI will catch it.

## Feature flags are compile-time and default off

2026-08-20 — `next.config.ts` maps five plain env vars onto `NEXT_PUBLIC_*` build flags: `BACKEND_RECORDING`, `NOTIFICATIONS`, `LIVE_THUMBNAIL`, `PREVIEW_ON_HOVER`, `INTERACTION_BINDINGS`. All default off, and `NEXT_PUBLIC_*` values are **baked in at build time**, not read at runtime. **How to apply**: changing a flag means rebuilding — restarting the server is not enough. Toggling one in a running dev server and seeing no effect is expected behaviour, not a bug. The Dockerfile takes the same names as `ARG`s, and the CI build job sets them explicitly (with `INTERACTION_BINDINGS: "true"` so that code path is compiled) — mirror those when reproducing a build failure.

## Server-only dependencies are declared external

2026-08-20 — `serverExternalPackages` in `next.config.ts` lists `@aws-sdk/s3-request-presigner`, `archiver`, `tar`, `bullmq`, `ioredis` and `web-push`: Node-only modules that must never reach the browser and that Turbopack should not parse into the module graph on every server compile. Next already ships `@aws-sdk/client-s3`, `sharp`, `prisma` and `playwright` in its own default external list, so only the uncovered ones are named here. The omissions are deliberate: `mediabunny` and `gif.js` power **client-side** recording and must stay bundled. **How to apply**: before adding to that array, check `node_modules/next/dist/lib/server-external-packages.json` — duplicating Next's list is noise. Never add a package the browser needs.

## The `/embed` route is deliberately framable

2026-08-20 — Every route keeps the browser's default same-origin framing except `/embed/:path*`, which `next.config.ts` serves with a `frame-ancestors` CSP. It defaults to `*` so a fresh install works as a public widget; `EMBED_FRAME_ANCESTORS` (space-separated origins) narrows it. **How to apply**: this is the one place where relaxing a security header is intended — do not "fix" it. Restricting it is a deployment decision made through the env var, not a code change.

## Persistence chain, and a rename done without SQL

2026-08-20 — `prisma/schema.prisma` holds `Preset` → `PresetSnapshot` → `Job` (plus `PushSubscription`). A preset is the mutable named configuration, a snapshot freezes its options, a job renders one. The models were renamed from `Template`/`TemplateSnapshot` but keep `@@map("Template")` and `@map("templateId")`, so the rename cost no migration and the database columns still say "template". **How to apply**: expect the old names in SQL, in migration files and in stored job paths; do not "clean them up" into a migration. The Prisma client is generated to `src/generated/prisma` (gitignored) — run `npx prisma generate` after pulling a schema change, or `npm install`, which does it via `postinstall`.

## Analytics is self-hosted Umami, tracked by hand

2026-08-23 — Google Analytics was replaced by a self-hosted, cookieless Umami instance (`src/lib/analytics/umami.ts`, `docs/analytics.md` for the full contract). Two choices are load-bearing and look like mistakes if you do not know why. **`data-auto-track="false"`**: Next navigates without reloading the document, so Umami's auto-tracking records one pageview per tab, or records later views carrying the previous page's title — `UmamiTracker` sends every view by hand from `usePathname()`/`useSearchParams()`, chaining the previous in-app URL as the referrer so internal pages are not all credited to the external source that opened the tab. **The pageview queue**: `strategy="afterInteractive"` injects the script *after* hydration, so the tracker's first effect runs before `window.umami` exists; an optimistic `window.umami?.track(…)` silently drops the initial view of every cold load. Queue when absent, drain in the script's `onLoad`. **How to apply**: never "simplify" either of those away, and never paper over the race with a `setTimeout` — it moves the race, it does not remove it. The config values are `NEXT_PUBLIC_*`, hence baked in at build time (see the feature-flag entry above) and declared as Docker `ARG`s; unlike the other `NEXT_PUBLIC_*` args they are deliberately not empty-defaulted, because an empty website id is the documented kill switch and would ship every image with analytics off.
